# Project Atlas performance report

**Status:** Historical, preliminary measurements; not a production performance claim. All results are from synthetic OHLCV data in an ARM64 Kali Linux VM on macOS, using C++20 Release builds. Exact host CPU and VM resource allocation were not recorded and remain a reproducibility limitation.

## Benchmark 001 — Repeated small-file ingestion

The benchmark performs 2,000 warm-up reads followed by seven trials of 20,000 reads of the same five-row CSV (`data/sample_ohlcv.csv`): 100,000 parsed records per timed trial. It includes repeated open/close overhead.

| Trial | Time (ms) | Records/s |
|---|---:|---:|
| 1 | 58.150 | 1,719,688 |
| 2 | 57.632 | 1,735,151 |
| 3 | 57.896 | 1,727,224 |
| 4 | 58.502 | 1,709,353 |
| 5 | 58.540 | 1,708,236 |
| 6 | 59.222 | 1,688,573 |
| 7 | 58.875 | 1,698,523 |

Minimum 57.632 ms; median 58.502 ms; mean 58.402 ms; maximum 59.222 ms. Median-based throughput: **1,709,353 records/s**.

## Benchmark 002 — Single large-file ingestion

Dataset: 100,000 synthetic consecutive calendar-day rows generated by `scripts/generate_benchmark_data.py` (approximately 4.6 MB). Two untimed warm-up file reads and seven timed full-file reads; each trial parses, validates and materializes 100,000 records.

One recorded seven-trial execution: minimum **24.366 ms**, median **24.497 ms**, mean **24.513 ms**, maximum **24.717 ms**; median-based throughput **4,082,107 records/s**.

Other recorded runs varied; an additional set of three execution medians appears in the prior report: 24.158 ms, 24.338 ms and 23.944 ms. They are separate executions and should not be merged into the seven-trial dataset.

### Process memory

Three GNU `/usr/bin/time` peak resident set size readings: **20,912 KiB**, **19,560 KiB**, **19,860 KiB**. These are whole-process RSS peaks, not parser-only allocations. They are not a memory-per-record measurement.

## Reproduce

```bash
python3 scripts/generate_benchmark_data.py --rows 100000
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release --parallel 2
./build-release/benchmark_csv
./build-release/benchmark_large_csv
/usr/bin/time -v ./build-release/benchmark_large_csv
```

Run from the repository root. Record compiler version, CPU, VM resources and background load when reproducing. Both benchmarks report elapsed wall-clock time with `std::chrono::steady_clock`.

## Interpretation and limitations

The large-file workload has higher observed throughput than the repeated small-file workload, but **the workloads differ**: this is not a demonstrated code optimization speedup. Timings include file IO, conversion, validation, allocation and caching effects; neither benchmark isolates pure numeric parsing latency. Synthetic calendar days do not represent real market sessions. Seven trials and a single VM do not establish production performance. Further work: profiling, allocation experiments, additional sizes, representative data, memory profiling, sanitizers and robust statistics.

## Benchmark 003 — Vector Capacity Reservation

### Objective

Evaluate whether preallocating storage for MarketBar records
improves CSV ingestion performance and peak memory usage.

### Implementation

CsvReader::read() accepts an optional capacity_hint parameter.

- Default: 0 (normal vector growth)
- Optimized: 100000 (reserve capacity before parsing)

The capacity hint is optional and does not change CSV
validation rules or the expected output records.

### Experimental Environment

- Kali Linux ARM64 virtual machine
- C++20, GCC 15.2.0
- CMake Release build
- Synthetic 100,000-record OHLCV dataset

### Timing Methodology

- 3 warm-up pairs
- 15 measured A/B pairs
- Alternating measurement order
- Same input dataset and parser implementation
- Median execution time used for comparison

### Timing Results

| Metric | Unreserved | Reserved |
|---|---:|---:|
| Median execution time | 24.347 ms | 23.205 ms |
| Median throughput | 4,107,311 records/s | 4,309,329 records/s |

Observed median execution-time reduction: 4.69%.

### Peak Memory Methodology

Each mode was executed in a separate process.

GNU time measured maximum resident set size (RSS).

| Trial | Unreserved (KiB) | Reserved (KiB) |
|---|---:|---:|
| 1 | 12424 | 9984 |
| 2 | 14376 | 10068 |
| 3 | 12648 | 10000 |
| 4 | 13012 | 10064 |
| 5 | 12504 | 10000 |

Median unreserved RSS: 12,648 KiB.
Median reserved RSS: 10,000 KiB.

Observed median peak RSS reduction: approximately 20.9%.

### Reproduction

Generate the dataset:

    python3 scripts/generate_benchmark_data.py

Configure and build:

    cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
    cmake --build build-release --parallel 2

Run the timing benchmark:

    ./build-release/benchmark_capacity

Measure peak memory:

    /usr/bin/time -f "Peak RSS: %M KiB" \
        ./build-release/benchmark_capacity_memory unreserved

    /usr/bin/time -f "Peak RSS: %M KiB" \
        ./build-release/benchmark_capacity_memory reserved

### Interpretation

For this workload, capacity reservation reduced median
execution time and peak resident memory usage.

These measurements are specific to the tested dataset,
compiler, build configuration, and virtualized hardware.

The experiment does not isolate allocation overhead
from other CSV parsing costs.

Peak RSS includes the entire process, not just the vector.

Capacity hints may waste memory when significantly larger
than the actual number of records.

Additional independent benchmark runs and profiling are
needed before generalizing these findings.

## Benchmark 004 — Fixed-Size CSV Field Splitting

### Objective

Evaluate whether replacing dynamically allocated CSV field
storage with a fixed-size array improves end-to-end ingestion
performance without changing parsing correctness.

### Implementation

Original implementation:

    std::vector<std::string_view>

Optimized implementation:

    std::array<std::string_view, 6>

The fixed six-column schema makes dynamic field-buffer
allocation unnecessary.

Both implementations use the same numeric conversion,
calendar validation, chronology checks, OHLCV validation,
and output record representation.

### Experimental Environment

- Kali Linux ARM64 virtual machine
- GCC 15.2.0
- C++20 Release builds
- Synthetic 100,000-record OHLCV dataset
- Same input file for both implementations

The original implementation was built from a separate
Git worktree at commit cb95011.

The optimized implementation was built from the working
tree containing the fixed-size splitter change.

### Timing Methodology

Both implementations used the existing large-file
benchmark executable.

Each benchmark invocation performs two warm-up reads
followed by seven timed full-file ingestion trials.

An external comparison script performed two additional
warm-up invocations per implementation and ten measured
invocations per implementation.

Execution order alternated between baseline and optimized
implementations.

Each reported comparison is the median from one
seven-trial benchmark invocation.

The final summary compares the median of those ten
per-invocation medians for each implementation.

### Timing Results

| Trial | Original (ms) | Optimized (ms) |
|---|---:|---:|
| 1 | 24.735 | 14.348 |
| 2 | 24.328 | 14.149 |
| 3 | 23.698 | 14.487 |
| 4 | 23.882 | 14.370 |
| 5 | 23.914 | 14.319 |
| 6 | 23.956 | 13.923 |
| 7 | 23.605 | 14.414 |
| 8 | 23.853 | 13.924 |
| 9 | 23.866 | 14.105 |
| 10 | 23.648 | 14.307 |

### Summary

| Metric | Original | Optimized |
|---|---:|---:|
| Median ingestion time | 23.874 ms | 14.313 ms |
| Median-based throughput | 4,188,657 records/s | 6,986,655 records/s |

Observed median ingestion-time reduction: **40.05%**.

Observed throughput increase: approximately **66.8%**.

These are workload-specific observations, not universal
performance guarantees.

### Peak Memory Comparison

Five separate-process comparisons used GNU time to
measure maximum resident set size.

| Trial | Original (KiB) | Optimized (KiB) |
|---|---:|---:|
| 1 | 20,932 | 21,536 |
| 2 | 20,992 | 21,524 |
| 3 | 19,608 | 19,828 |
| 4 | 21,244 | 20,048 |
| 5 | 20,840 | 20,256 |

Median original peak RSS: 20,932 KiB.

Median optimized peak RSS: 20,256 KiB.

The difference between these medians is approximately
3.23%, but the individual measurements are mixed.

The optimized process used more memory in three of five
paired trials.

Therefore, these results do not establish a reliable
memory reduction.

Peak RSS includes the entire process rather than
isolating field-splitting allocations.

### Correctness Verification

Seven automated CTest suites passed in both Debug
and Release configurations.

The regression coverage includes:

- Missing CSV columns
- Extra CSV columns
- Malformed numeric values
- Floating-point overflow
- NaN input rejection
- Negative unsigned volume
- Unsigned volume overflow
- Existing OHLCV and chronological validation

### Interpretation

The fixed-size splitter substantially improved
end-to-end ingestion time in this controlled experiment.

The change avoids dynamic allocation for the temporary
field-view collection on each CSV row.

However, the benchmark does not isolate allocation
overhead from the remaining parsing and validation work.

Additional hardware platforms, larger datasets,
independent repetitions, and profiling would strengthen
the evidence.

## CPU Profiling Investigation

### Methodology

A separate profiling workload processed 20,000,000
records through repeated CSV ingestion.

The profiling build used GCC instrumentation flags:

    -pg -g -fno-omit-frame-pointer

GNU gprof was used to inspect the resulting profile.

### Recorded Findings

The profile reported approximately:

- 63.13% of sampled time in CsvReader::read
- 9.53% in parse_number<double>
- 25.01% attributed to _init
- 2.38% attributed to main

The profiling sample total was approximately 0.84 seconds.

### Interpretation

CsvReader::read dominated the recorded profile.

The results motivated investigation of field splitting
and temporary allocations.

However, gprof instrumentation, compiler behavior,
sampling granularity, and symbol attribution limit
the precision of these percentages.

The percentages should not be interpreted as exact
production CPU utilization or definitive attribution
of individual parsing operations.

Profiling results must not be directly compared with
ordinary uninstrumented Release benchmark timings.

## Reproducibility and Limitations

All reported experiments used synthetic market data.

The measurements were collected in a virtualized
ARM64 development environment.

Results may vary with:

- CPU architecture and frequency
- Virtual machine scheduling
- Compiler version and optimization flags
- Filesystem caching
- Background system activity
- Allocator behavior
- Dataset size and content
- Measurement order

The experiments do not represent live trading latency,
exchange connectivity, or production execution systems.

The original and optimized implementations were compared
under equivalent Release configurations, but full
compiler command lines and host CPU details were not
archived.

Future work should include sanitizers, additional
dataset sizes, more independent benchmark sessions,
and performance measurements on native hardware.
